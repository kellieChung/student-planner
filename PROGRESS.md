## Canvas & extension
- Extension (`canvas-extension/`) reads Canvas with the student's own session and posts to `app/api/canvas/sync` via a `Bearer` `ExtensionSession` token (Canvas gives students no tokens). **Pairing:** the extension generates a random state and opens `/extension-login?state=`; `/extension-callback` is a Connect confirmation whose server action creates the session (token stored as sha256, `lib/extensionAuth.ts`) and returns the plaintext only to that page, which `postMessage`s it; `site-bridge.js` (content script on the app origin) relays it and `background.js` accepts it only for its own stored state. No pollable exchange endpoint. Sign out revokes (`DELETE /api/extension/auth/session`); password change deletes all sessions. Sync is per-course fault-tolerant (`failedCourseIds` are not pruned), sends only fields ingest reads, fetches announcements with explicit `start_date`/`end_date` (Canvas defaults end to start+28d), and the popup renders from `canvasSyncProgress` storage. Follows `Link` header pagination. Popup follows the app's Night/Day theme.
- Popup: Night/Day tokens, bundled Manrope/Spectral, inline-SVG icons (no emoji), single `state`→`render()`, real brand mark icons. Sync button is replaced by progress+Cancel while running; status chips are flat non-interactive pills; restore-a-course sits in a closed Troubleshooting `<details>`; header constellation lights per step (signed in, Canvas connected, synced). Canvas URL is auto-detected from open tabs (hostname heuristic, then `IS_CANVAS_PAGE` reply from `content.js`), else `[name].instructure.com` or a pasted full host; connect verifies `/api/v1/users/self`. No school list, no debug URL override (both declined).
- **Complete tasks when submitted in Canvas (2026-10-03, user decisions: default ON, normal XP):** `PlannerSettings.completeFromCanvas` (taskbar settings → Canvas). Assignments are fetched with `include[]=submission`; the extension sends `submitted` + local `completed_day`/`due_day` (server can't know the timezone). `lib/canvasCompletions.ts` stores `Assignment.canvasSubmitted` (null = unknown/old build) and completes + awards XP (`lib/xpAward.ts`, shared with `/api/gamification`) only on a flip to true, so a manual un-check sticks. Consequence accepted: the first check awards XP for every past submission never checked off by hand. Turning the setting back on backfills (no completedAt, no late penalty). Triggers: full Sync/restore, `POST /api/canvas/completions` from the extension's light check (per-course assignments only), run on Canvas page loads on the connected host, Lodestar tab focus (site-bridge), and a 15-min alarm; ≥30s apart with a trailing alarm. The planner reloads customizations/XP/Starlight on refocus and on `LODESTAR_CANVAS_COMPLETIONS_APPLIED`. Auto-completed tasks get `TaskCustomization.completedFromCanvas` → a green "Canvas" pill (tooltip) on the completed card; server-owned, cleared whenever the task is un-completed (PATCH route + `persistCustomization`). Only assignments a full sync already created are checked; paper/no-submission work never auto-completes.
- **Starlight rebalance + Southern Sky expansion (2026-10-04, user decisions: ~3x slower, keep existing balances, no Starlight for Canvas catch-up, buyable region):** see gamificationSystem.md → Economy for the numbers. Existing users keep old-scale balances and lifetime totals (about 2.5× richer than the new scale), and some early stars got *cheaper* in absolute terms, so judge the pace on a fresh account. - **Complete-from-Canvas DB cost (2026-10-04, extension 0.3.1):** Prisma Postgres bills per operation and the light check posted every assignment every run (~5 ops even when nothing changed, plus ~6 per planner refocus reload): ~12–15k ops/month per active student. Now the extension keeps `submittedCache` (`{ canvasOrigin, entries: { "course:assignment": bool } }`) of the state Lodestar last accepted and posts only differences, so an unchanged check makes no request. The cache is written after a 2xx from the light check, full sync or restore, **but not when the response has `deferredCount > 0`** (`applyCanvasCompletions` handles at most 40 per call; caching would strand the rest). ## AI pipeline (Claude Haiku primary, Ollama fallback)
- Every AI call uses Haiku when `ANTHROPIC_API_KEY` is set, else local Ollama; each has a timeout and deterministic fallback. Shared `lib/ai/anthropicClient.ts` (`logAnthropicUsage`), `lib/ollamaConfig.ts` (`NUM_CTX=8192`). **Any Canvas HTML must go through `lib/htmlText.ts` (`stripHtml`/`truncateText`) before a prompt** (unbounded HTML once blew the context window). XP is type-based (`lib/xp.ts`), server-side, no model call.
- Cost control (target ≤ ~$0.05/user/week): `Announcement.aiAnalyzedHash` skips unchanged text (set only on real extraction with no degraded dup check; legacy reviewed announcements are backfilled without a call); extraction batches 10/call, dup check is one call per batch (exact/containment pre-pass, containment capped at medium confidence); assignment scoring batches 20/call; `/api/task-planning` reuses matching stored estimates, only scores the user's own task ids, caps 200 analyses/24h, and never stores fallback results. No prompt caching/Batches (prompts under Haiku's cache minimum; Batches is async).
- The duplicate checker is biased to false positives in code (`uncertainDuplicateResult`); `checkStatus` `"checked"` vs `"degraded"` (only degraded shows grey "unavailable"); matches resolve by 1-based number, never a model-typed id.
- Extraction failures retry by bisection; the `RULES` block goes only in the system message.
- **Reading lists (2026-09-26):** extraction used to miss link lists under "Readings/Videos"/"Read before class" headings (seminar readings). Now: prompt text keeps line breaks (`stripHtmlKeepLines`), Canvas `screenreader-only` spans are removed from both prompt and display text (evidence must match the display copy), RULES make one task per listed item, "before or after class" is required (only explicitly optional work is low), Anthropic extraction uses `temperature: 0`. Old announcements aren't re-run automatically (content-only hash). The check panel has an "Already checked (N)" expander (dry-run `checkedPreview`) to tick specific ones; ticking any sends `regenerate: true` with `selectedAnnouncementIds` (1 check, shares the 10-per-check cap with new ones). Not click-tested signed-in.
- Duplicate guard: a model "high" match whose week/part/chapter/section numbers (incl. 第N周/节) conflict with the task's is capped at medium (`hasConflictingNumbers`) so it surfaces instead of being auto-suppressed. The exact-name pre-pass ignores one leading verb ("Complete REFLECT: X" = "REFLECT: X", high). Checker instructions: prep steps the assignment doesn't name are at most medium. **Still open:** a vaguely named task can still be wrongly suppressed (an unnumbered "Complete pre-assignment" → "Week 3 Monday Pre-assignment"), and auto-suppressed items are invisible to the user.
- Quota (`lib/aiRateLimit.ts`): 2 checks/week + bonus credits (spent weekly-first), all derived from `AiTaskEvent` rows (`detection_pass_triggered/paused`, `detection_credit_granted`); credit-paid runs don't count against the week. `DEV_ACCOUNT_EMAILS` only unlocks `/dev` and `/api/dev/*` (no rate-limit bypass). Per-check cap `MAX_ANNOUNCEMENTS_PER_CHECK = 10` (`lib/analysisLimits.ts`, newest first; >10 explicit selection is a 400); resume is restricted to the run's charged ids. Pause/resume is cooperative (one stream; pause event checked before each batch; resume free within 24h). **Regenerate** re-runs the range (1 check) and replaces a same-key pending candidate (a re-worded task can resurface a declined one). `/dev` dashboard: accounts/credits, analyzer reset, tour/map launchers; all `/dev/*` go through `requireDevUser` (404 otherwise).

## Planner, scoring, scheduling
- Priority (`lib/prioritization.ts`, spec `prioritizationModule.md`): earliest act-by day wins (finish → real due day, start → latest-start day), then least slack (hours until due − work time − procrastination shift) within the day; importance/difficulty/consequence/frog only break ties (≤ 6h). Planner reads type/minutes from `resolvedPlanning`, not raw `taskPlanning`. A future custom start date forces score 0 (gate, not a weight; overdue wins over a stale `startAt`); explicit Focus is ungated. Procrastination index per type shifts effective due dates earlier (capped). Time estimates are a type→minutes lookup (`estimateMinutesByType`), overridable per task (`TaskCustomization.estimatedMinutesOverride`, planning only); auto-estimation covers open, not-past-due tasks due within 10 days, max 60; the server only calls the AI when Canvas type/name can't settle the type.
- `Assignment.due` is plain `"YYYY-MM-DD"`; `dueAt`/`dueFraction` resolve in the browser's timezone. **Never pass a server-built `Date` day-anchor to the client** (this once shifted every task a day) and never use `new Date("YYYY-MM-DD")`/`toISOString()` for a calendar day — use `parseLocalDate`/`toDateKey`/`getTodayString`/`daysBetween` (`lib/utils.ts`). The announcements route takes window instants + `tzOffset` from the browser; `recurring-tasks/[id]` takes the browser's `today` (`resolveClientToday`); `task-customizations` stores `completedAt`/`startAt` as UTC-midnight date keys (round-trips). Week is Sunday-start (`getStartOfWeek`).
- State is per `(userId, taskId)` in `TaskCustomization`/`CustomTask`/`TaskPlanningEstimate`/`ProcrastinationRecord`. `persistCustomization`'s PATCH is a full-row replace: **spread the current customization before overriding**. Overrides: `nameOverride/typeOverride/dueAtOverride/course`; `typeOverride` is the only storage for a custom task's type; `dueAtOverride` is one instant (date-only overrides synthesize `endOfDayInstant`). `completedAt`/`startAt` are `"YYYY-MM-DD"`. Custom start dates lapse at read time (`hasCustomStartDatePassed`), never via a PATCH. Task status is derived 3-way (`lib/taskStatus.ts`).
- Weekly grid: chronological (due → time → course), absolutely positioned via `packColumnOffsets` (skyline packer; not CSS Grid rows); completed cards shrink/dim but never move; small gaps are expected (greedy first-fit).
- Card label defaults to `COURSE - TYPE - DAY - NAME` (`lib/taskLabel.ts`), per-user order/visibility in `PlannerSettings.taskLabelParts`; type code HW/R/EXAM/TODO (TODO = personal `Course.isCustom`); the 14-value `AssignmentType` still drives scoring. Course abbreviation/colour are user-editable `CanvasCourse` columns with hash defaults (`lib/courseColor.ts`).
- Recurring tasks: `RecurringTask` template; occurrences are real `CustomTask` rows (deterministic ids `custom-r<id>-<due>`) materialized client-side (`expandOccurrences`, 8-week horizon, on mount). Deleting one occurrence is a `TaskCustomization` tombstone (hard delete would resurrect). Scope prompt "this / this and following" (`applyFromDate`, `deleteFrom`); refetch (`refreshCustomTasks`) after series changes.
- Localstorage-only by design: pomodoro state/active task, theme, music volume, window layout.
